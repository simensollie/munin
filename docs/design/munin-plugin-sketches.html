Munin bar plugin

Detects a Teams call from PipeWire and the window title, asks once before recording, and keeps the state visible in the top bar until the transcript has landed. Microsoft 365 supplies the agenda and the attendee list; a local voice register keeps speaker names consistent from one meeting to the next.

2026-09-14 local.munin kinds: service, bar-widget Omarchy 4.0.0.alpha
State machine

Seven states, one of them visible at a time

The bar widget renders exactly one state. The rule that makes the whole thing trustworthy: nothing moves from detected to recording without a human saying so.

In place

Where it sits in the bar

Right section, immediately left of the tray, so it sits with the other status widgets rather than competing with the clock.

Prompts

The three things it tells you

Omarchy's notification daemon reports actionsSupported: true, so both prompts can carry real buttons. The keybind is offered alongside, never instead — the notification can be missed, the keybind cannot.

Panel

Click the indicator

A dropdown in the same idiom as the audio and network panels — qs.Ui's Panel base gives the popup, the keyboard navigation and the IPC open/close for free.

Detection

Teams arrives in three shapes

Native client, installed PWA, or a tab in Chromium. They announce themselves differently, and only one of them says "Teams" to PipeWire — so identity and activity have to be established separately.

ShapePipeWire saysWindow saysIdentified by

teams-for-linux		 application.name
= Teams		 class teams-for-linux PipeWire alone is enough
Installed PWA Chromium class chrome-teams.microsoft.com__-Default Window class
Browser tab
the case on this machine today		 Chromium title contains Microsoft Teams Window title
A
A call is live: one process holds a playback stream and a capture stream at once Read from Quickshell.Services.Pipewire inside the plugin — no polling of pw-dump. This condition alone removes the false-positive class: a video playing in a tab has playback but no microphone. True for all three shapes.
AND
It is Teams: any one of the three identifiers above matches Match on the PipeWire client first, since the native app is unambiguous and costs nothing. Fall back to the Hyprland window belonging to that stream's PID and test class, then title. A browser with no Teams window open never passes, however many tabs are making noise.
→
Prompt once, then stay quiet One notification per call. Dismissing it does not re-ask; the widget stays in detected so the keybind and the panel remain available.

Keeping identity separate from activity is what makes the other platforms a configuration change rather than a rewrite: Zoom, Meet and Slack are additional entries in the identifier table, and condition A is already true for all of them.

Known conflict: voxtype.service is running on this machine and also wants the microphone. PipeWire allows multiple readers in principle, but this has to be confirmed on hardware before it bites in the middle of a real meeting.

Context

What Microsoft 365 is asked for

The calendar never starts a recording. It answers the questions a recording cannot answer for itself: what this meeting is called, who is in it, and what it is about.

PulledFromUsed for
Subject, start, end, organiser Outlook calendar event Session title and folder name, replacing the timestamp fallback
Attendees + response status Outlook calendar event The closed set for speaker assignment. Four candidates is a far easier problem than open-set identification
Body / agenda text Outlook calendar event Decode-time glossary bias. An invite naming a customer promotes that customer's vocabulary into the ~40 terms Whisper's prompt can hold
Recurring series id Outlook calendar event Makes "never record this meeting" stick to the series rather than one instance
Actual join / leave times Teams attendance report Who was really there, and when. Narrows the candidate set per segment rather than per meeting

The attendance report may not be available to you

Join and leave times come from Graph's online-meeting artifacts, which are typically gated behind tenant-admin consent rather than user consent. Assume the invite list is what you get, and treat the attendance report as an upgrade to request separately. The closed-set assignment works either way; it is just less sharp.

Voices

A register of who sounds like whom

A voice profile is a name and an embedding. Once someone is in the register they are named correctly in an ad-hoc call with no invite, in a meeting where the attendee list is wrong, and in a transcript written six months from now.

One transcript

Name a speaker

Assign SPEAKER_01 a name here and now. Nothing is stored beyond the label on this transcript. Fast, reversible, and enough for anyone you meet once.

Every transcript

Enrol a voice

Store an embedding so the same person is recognised automatically from here on. One extra click at the moment you already know who it was.

Two actions rather than one keeps the register small enough to stay accurate. Every profile you add is another candidate the matcher has to discriminate against, so enrolling the six colleagues you meet weekly gives better results than enrolling everyone who ever joined a call. The register is worth pruning, which is why the admin view leads with match confidence and last-heard rather than with a count.

Attribution becomes four tiers

TierMethodError rate
1 · YouEnergy on track 1 and not track 2None. True by construction — no model involved
2 · EnrolledEmbedding match against the register, above thresholdLow, and measurable. Confidence stored per segment
3 · InvitedClosed-set assignment against the attendee listModerate. "Which of these four" not "who is this"
4 · UnknownPositional label kept: SPEAKER_02Honest. Better a positional label than a confident wrong name

What a profile holds

Keep the clips, not just the centroid

An embedding only means anything to the model that produced it, so changing the embedder invalidates every profile at once. Retaining the enrolment clips turns that from re-enrolling everyone into munin voice reembed --all. It is a few minutes of audio per person and the only thing standing between you and starting the register over.

Admin

Administering the register

A local tool at munin admin, loopback only. The bar panel links to it and never embeds it — a consent record and an audit log want a table, not a dropdown.

Same actions from the CLI

munin voice list the register, as above munin voice enrol "Ola Nordmann" --from <session> --speaker 2 munin voice add-sample ola --from <session> --speaker 1 strengthens a thin profile munin voice rename ola "Ola Nordmann" munin voice disable ola keeps the profile, stops matching munin voice delete ola munin voice reembed --all after a model change, from retained clips munin review the queue, in the terminal
Storage

Everything under ~/munin/

One named root so a stray folder in your home directory says what it is and what put it there. Recordings are chronological on disk, because that is the only ordering that never needs rewriting; everything else is a symlink view, cheap to rebuild and safe to delete.

~/munin/ ├── recordings/ │ └── 2026/09/ │ ├── 2026-09-14T1325-weekly-quality-sync/ │ │ ├── session.json state, title, source, calendar id, sink, checksums │ │ ├── mic.opus track 1 — you, 24 kbps mono │ │ ├── app.opus track 2 — everyone else │ │ ├── mixed.mp3 64 kbps, for anything that wants one file │ │ ├── transcript.txt [HH:MM:SS - HH:MM:SS] Speaker: text │ │ ├── transcript.json word timings, confidences, speaker turns │ │ └── markers.json anything you clicked "add marker" on │ └── 2026-09-14T1030-deviation-review-line-2/ │ └── … │ ├── by-title/ symlinks, regenerated on write │ ├── weekly-quality-sync/2026-09-14 → ../../recordings/2026/09/… │ └── management-review/2026-09-11 → ../../recordings/2026/09/… │ ├── by-participant/ only for calendar-matched sessions │ └── ola-nordmann/ → … │ ├── inbox/ captured, not yet transcribed │ └── 2026-09-14T1410-untitled → ../recordings/2026/09/… │ ├── voices/ the register │ ├── ola-nordmann.json name, embedding, samples, accuracy │ ├── kari-nordmann.json │ └── samples/ enrolment clips, kept so profiles survive a model change │ ├── config.toml transcription backends, detection, paths ├── munin.log └── latest → recordings/2026/09/2026-09-14T1325-weekly-quality-sync

Two properties worth keeping: the directory name alone tells you when and what without opening anything, and grep -r across the tree searches every transcript you own with no index to maintain. session.json is the only file the worker writes state into, so a half-finished session is always identifiable after a crash.

Backends

Where transcription happens is configuration

The recorder never knows who transcribes. Three backends satisfy one interface, ordered into a fallback chain, so a meeting captured on a machine with no GPU still gets a transcript without you doing anything.

BackendRuns on60-min meetingSuits
local This machine, faster-whisper on CUDA or whisper.cpp on Vulkan 5–8 min on a 3070
30–40 min on an iGPU		 The desktop. No network, no dependency on anything being awake
ssh Another machine you own — audio pushed, transcript pulled back 5–8 min
+ ~20 s transfer		 The mini PC records, the desktop does the work. 11 MB of Opus makes the transfer irrelevant
api Any OpenAI-audio-compatible endpoint, gateway or hosted 5–6 min A shared cluster, or borrowing capacity you do not own

The API backend splits the pipeline

The OpenAI audio API returns text and optionally word timings. It has no speaker field, so diarization and voice matching cannot go through it and always run locally regardless of where the words came from. That is the cheaper half, and track 1 already identifies you for free, so the split costs little — but it means api is not a way to run Munin on a machine with no compute at all.

~/munin/config.toml [transcribe] backend = "local" primary fallback = ["ssh", "api"] tried in order; session stays spooled if none answer [transcribe.local] device = "cuda" cuda | vulkan | cpu compute_type = "float16" model_no = "NbAiLab/nb-whisper-large" model_en = "openai/whisper-large-v3" keep_warm = true both models resident — load dominates inference at this volume [transcribe.ssh] host = "desktop.lan" user = "siso" remote_bin = "~/.local/bin/munin" same binary, run with --worker-only transport = "rsync" [transcribe.api] endpoint = "https://gateway.internal/v1/audio/transcriptions" model_no = "nb-whisper-large" model_en = "whisper-large-v3" api_key_cmd = "secret-tool lookup service munin-api" never the key itself [diarize] device = "cuda" always local, whatever the ASR backend
Install

One command, one wizard, one check

Installing should not require reading any of the above. The installer puts files in place and changes nothing it cannot list; the wizard asks the four questions that have no sensible default; the doctor tells you which of them is wrong.

$ git clone https://github.com/…/munin ~/dev/munin && ~/dev/munin/install.sh

What the installer does, in order

#StepTouches

3Install and validate the shell plugin~/.config/omarchy/plugins/local.munin/

Models are not downloaded here. munin models pull is a separate, explicit 6.2 GB — an installer that silently spends that much of someone's connection is an installer people stop trusting. The wizard offers it at the right moment and the CLI works without it against a remote backend.

The doctor is the thing worth building first. Every open question in this document ends up as a line in that output, which turns "is this set up correctly" from an afternoon of checking into one command — and makes a broken install self-describing when you come back to it in six months.

Uninstall is part of install

install.sh --uninstall removes the binaries, the plugin, the bar entry, the keybind and the unit, and leaves ~/munin/ exactly where it is, printing the path. Nothing you recorded is ever removed by an uninstaller.

Build

What the plugin actually is

Two kinds in one plugin folder: a service that watches and records, a bar widget that renders and asks. The heavy lifting stays in a daemon outside the shell.

~/.config/omarchy/plugins/local.munin/ ├── manifest.json schemaVersion 1, kinds: ["service","bar-widget"] ├── Service.qml PipeWire watch, Hyprland titles, notifications, IPC ├── BarWidget.qml extends qs.Ui Panel — button + dropdown + IPC target ├── Model.js state machine, session list, formatting └── components/ ├── TrackMeter.qml └── SessionRow.qml ~/munin/config.toml read by the daemon and the worker, not by the plugin ~/.local/bin/munin CLI — what the keybind, the buttons and the wizard all call

The plugin talks to the daemon over IPC — omarchy-shell local.munin toggle from the keybind, and the daemon's own socket for state. Validate the folder before enabling it: omarchy plugin validate ~/.config/omarchy/plugins/local.munin.

Unresolved

Decisions this sketch is waiting on

Microphone contention with voxtype
Both daemons want the default source. Needs ten minutes on the hardware to confirm. If PipeWire refuses the second reader, the fix is a mediating capture service both use — a design change, not a tweak.
Is SUPER+SHIFT+R free?
Not in the user bindings file, which usually means Omarchy owns it. omarchy menu keybindings --print settles it; if taken, hl.unbind first.
Does "never for this meeting" persist against the calendar event, the series, or the title?
A recurring 1:1 you never want recorded should stay unrecorded without asking again. That needs the recurring event id, not the instance.
How does the SSH backend authenticate unattended?
The worker runs from a systemd user unit with no terminal, so a passphrase-protected key needs an agent that is already unlocked, or a dedicated key with no passphrase restricted to one command. The second is less elegant and more likely to still work in a year.
Retention period for audio
Transcripts are small and worth keeping indefinitely. Audio is 11 MB an hour and its value drops sharply once the transcript is verified. A default of "audio 90 days, transcripts forever" would keep the store bounded without losing anything you reach for.
Does the register survive a model upgrade?
Embeddings are specific to the model that produced them, so changing the embedder invalidates every profile at once. Re-embedding from retained samples is the way out, which is an argument for keeping enrolment clips rather than only the centroid.
